# PhonePe Standard Checkout setup

This project uses PhonePe's hosted **Standard Checkout** through the official
`@phonepe-pg/pg-sdk-node` package. The application never collects card details,
UPI PINs, or PhonePe credentials in the browser.

## Before enabling it

1. Deploy the backend to a public HTTPS URL. The repository root's
   [`render.yaml`](../render.yaml) blueprint does this; the existing
   `vercel.json` deploys only the Vite frontend and cannot receive PhonePe's
   webhook. See [Deploying the API on Render](#deploying-the-api-on-render).
2. Deploy the frontend and set `VITE_API_URL` to the deployed backend's
   `/api` URL.
3. Use MongoDB Atlas or another MongoDB replica set. A verified payment finalises
   the cart and sales counts in a transaction, so a standalone MongoDB server is
   not sufficient for online payments.

## Deploying the API on Render

The blueprint deploys `backend/` as a Node web service, runs `npm ci`, starts
`npm start`, and health-checks `/api/health`.

1. Create a **MongoDB Atlas** cluster first — the free M0 tier is a replica set,
   which the paid-order transaction requires. Under *Network Access*, allow
   Render's outbound traffic (`0.0.0.0/0` is the practical choice, since Render
   does not publish static outbound IPs on the free and starter plans; the
   database stays protected by its user credentials).
2. In Render: **New → Blueprint**, select this repository, and let it detect
   `render.yaml`.
3. Render prompts for each `sync: false` value. Set `MONGODB_URI` and
   `FRONTEND_URL` now. Leave the five `PHONEPE_*` secrets blank on the first
   deploy — `PHONEPE_ENABLED` defaults to `false`, so checkout fails closed
   until they are filled in. `JWT_SECRET` is generated by Render.
4. Deploy, then confirm `https://<service>.onrender.com/api/health` returns
   `success: true`.
5. Set `VITE_API_URL=https://<service>.onrender.com/api` on the frontend and
   redeploy it, so the browser calls the deployed API rather than localhost.

`FRONTEND_URL` must be the exact public frontend origin, with no trailing
slash and no path — it is matched against the browser's `Origin` header for
CORS and used to build the PhonePe return URL.

### Free plan and webhook delivery

The blueprint defaults to Render's `free` plan, which spins the service down
after roughly 15 minutes of inactivity. A cold start can take longer than
PhonePe's webhook timeout, so a webhook may be missed; the return page's status
check still resolves the receipt, which is why sandbox UAT works on the free
plan. Change `plan: free` to `plan: starter` in `render.yaml` before taking
live payments, so webhooks arrive at a warm service.

## Backend environment

Copy the PhonePe entries from [`.env.example`](.env.example) into the deployed
backend's secret manager. Do not put any of these values in a `VITE_*` variable
or commit them to Git.

Set `PHONEPE_ENV=sandbox` while testing. In the PhonePe Business Dashboard's
Test Mode, copy the Client ID, Client Secret, and Client Version into the
matching variables. Generate strong webhook username/password values, configure
the dashboard's webhook as **SHA authentication**, and use:

```text
https://<service>.onrender.com/api/payments/phonepe/webhook
```

Subscribe to `checkout.order.completed` and `checkout.order.failed`. PhonePe
requires a valid HTTPS listener and may deliver duplicate webhooks; this code
verifies the callback and makes paid-order fulfilment idempotent.

With `FRONTEND_URL` set as above, PhonePe returns the customer to:

```text
https://shop.example.in/payment/phonepe/return
```

Finally set `PHONEPE_ENABLED=true` and restart the backend (on Render, saving an
environment variable redeploys automatically). Keep it `false` until all values
are present; checkout then fails closed rather than creating a payment with
incomplete credentials.

## UAT checklist

1. Place a PhonePe sandbox order and complete payment.
2. Confirm the webhook returns HTTP 200 and the order changes to `paid` and
   `confirmed`.
3. Confirm the browser return page also resolves the receipt through the status
   API, even if the webhook is delayed.
4. Deliver the same webhook twice and verify the cart and `soldCount` are
   changed only once.
5. Test failed and abandoned checkout: the cart must remain intact and the
   order must not be confirmed.
